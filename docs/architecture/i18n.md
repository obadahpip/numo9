# Localisation (A-10-T13, A-10-T14)

English (Canada) is the source language and the default; French (Canada) has every key from day
one (French text arrives in Phase 6, X-02). Canadian terms are enforced by the glossary lint
(A-10-T15).

## Web app (Next.js, A-10-T13)

| Piece | Where |
|---|---|
| Runtime | next-intl — `frontend/src/i18n/request.ts` (request config), `NextIntlClientProvider` in the root layout |
| Catalogues | `frontend/messages/en-CA.json`, `fr-CA.json` — nested keys, ICU MessageFormat (`{count, number}`, plurals) |
| Locale | `numo9_locale` cookie (written from the user's preference, A-02), else the browser's `Accept-Language` (`fr`, `fr-FR` → fr-CA), else en-CA. No locale in the URL: `/o/:org/…` is the same in every language. |
| Pseudo-locale | `en-XA`: en-CA text accented, +30 % long, bracketed — `[Šéţţîñĝš ~~~]`. Generated at load time, never in production unless `NUMO9_PSEUDO_LOCALE=1`. Playwright checks 360 / 1280 px layouts in it (`frontend/e2e/i18n.spec.ts`). |
| Writing messages | `defineMessages({ key: { id, defaultMessage, description } })`; `useFormatMessage()` in components, `await getFormatMessage()` (`@/i18n/server`) in async server components and metadata. |
| Gates | eslint `formatjs/no-literal-string-in-jsx` (hard-coded JSX text and accessible attributes fail — tested in `src/i18n/lint.test.ts`), `formatjs extract` + `check_i18n.py frontend` (every key in en-CA and fr-CA). |

## API (Django, A-10-T14)

| Piece | Where |
|---|---|
| Request language | `numo9.i18n.middleware.LocaleMiddleware` (after authentication, before tenancy): the signed-in user's `locale` → `numo9_locale` cookie → `Accept-Language` → en-CA. Responses carry `Content-Language`. |
| Without a request | `numo9.i18n.locale.locale_for(user=…, organisation=…)` / `override_for(…)` for emails, PDFs and jobs: the recipient's locale, else `Organisation.locale`, else en-CA. |
| Catalogues | `backend/locale/<en_CA, fr_CA>/LC_MESSAGES/django.po` (`make i18n` = makemessages); `.mo` files are build output of `backend/tools/compile_messages.py` (image build, dev start, test session) and are not committed. |
| Error messages as keys | `numo9.i18n.errors`: every API error is a stable dotted key plus a gettext message (`define("tenancy.unknown_practice", _("…"))`). Request-level errors answer `{"detail": "<localised>", "code": "<key>"}`; field errors keep DRF's `{"field": ["<localised>"]}` with the key as each message's code. |

Known limit: the middleware sees the user of session authentication (the web app). Token
authentication for the mobile apps (Phase 7) authenticates inside DRF and must activate the
user's locale there.
